# 0013. Metal tile renderer: placement, tile shape, shader delivery, overlay layering
Date: 2026-07-07
Status: accepted
Context: BUILD_SPEC §5.3 specifies an MTKView Metal tile renderer (atlas texture, colormap LUT in the fragment shader, frequency-axis LUT, LOD selection with a 100 ms cross-fade, placeholder stretching while tiles load) plus overlays (playhead, selection, magic-selection ribbons, curve lanes). The headless dev environment cannot compile or run Metal; only IndraKitCore/Net are CI-tested on Linux, and a macOS CI job compile-checks (but cannot run) the app. Several placement/format decisions were open.
Decision:
1. **Placement — math in IndraKitCore, Metal in IndraApp.** All decisions with a formula are pure IndraKitCore types with Linux tests: `AtlasIndex` (LRU slot allocation), `SpecRenderPlanner`/`TileQuad` (viewport → textured quads, coarser-LOD placeholder stretch, missing-tile lists), `LodFade` (cross-fade weights), `FrequencyLUT` (screen-row → bin-fraction table), `MagicSelection` (result_ref → ribbons → screen rects), `FeatureTable` (curve wire type). The IndraApp side (`SpectroRenderer`, `SpectroCanvasModel`, `SpectroMTKView`, `SpectrogramPane`) only encodes what the plan says and translates NSEvents. No separate IndraKitApple render target: the renderer needs AppModel/APIClient wiring that lives in the app anyway, and the app target is already the designated smoke-test surface (ADR 0012).
2. **Tile shape — full-height slabs in a `texture2d_array` atlas.** Tiles are 512 columns × nBins bins with canonical bounds `[c0, c1, 0, nBins]`, one atlas slice per tile (r8Unorm, nBins wide × 512 tall — matching the C-order (frames, bins) payload of `/spec/tile`, so uploads are memcpy-shaped, no transpose). Frequency zoom/pan/scale never touches tile keys: the fragment shader remaps screen y → bin through a 1D r32Float LUT rebuilt from the Viewport (linear or log) — rather than the §5.3 sketch of 512×256 sub-tiles, which would make cache keys unstable under frequency navigation and force key churn on vertical pan. 128 slices ≈ 128 MB at nFft 4096, inside the §4.7 256 MB budget; a 64 MB byte-level TileCache backs re-uploads after eviction.
3. **Shader delivery — runtime compilation from a Swift string constant** (`device.makeLibrary(source:)`), not `.metal` resources. SwiftPM's Metal-toolchain resource compilation is unreliable for executable targets (and unverifiable headlessly); a source string always compiles at launch (~ms, once), and failures surface as a visible `initError` in the pane instead of a silent missing-resource crash. Fallback if the runtime path ever regresses: move the same source into a `.metal` resource and load `device.makeDefaultLibrary(bundle:)`, keeping the string as the documented reference.
4. **Overlays — SwiftUI Canvas layer above the MTKView**, not extra Metal pipeline states (§5.3 sketches same-pass overlays). Playhead line, selection rectangle, ribbon fills, and per-pixel-column curve-lane envelopes are a few thousand immediate-mode primitives at most; both layers compute every coordinate from the same `Viewport` value in the same main-actor update, so they cannot drift. This keeps overlay iteration in ordinary SwiftUI. Revisit (move lanes/ribbons into the Metal pass as vertex buffers) if smoke tests show overlay lag during sustained 120 Hz pan/zoom.
5. **Frame pacing — draw-on-demand** (`isPaused = true`, `enableSetNeedsDisplay = true`, redraw pokes on state change; ~60 Hz self-pokes only while a LOD cross-fade is animating). `CAMetalDisplayLink` + triple buffering (§5.3) is deferred until continuous-animation workloads exist (scrolling playback follow); the on-demand model matches the current interaction set and is far simpler to reason about headlessly.
6. **LOD cross-fade** — plans snap to the TilePlanner-chosen LOD; on a change the outgoing LOD's plan keeps drawing fully opaque underneath while the incoming LOD's quads fade in over 100 ms (`LodFade`), premultiplied-alpha blending. Missing tiles render as the finest fully-resident coarser LOD stretched over the gap (`SpecRenderPlanner.placeholderQuads`).
Consequences: The compile-risky surface (Metal/AppKit) is thin and hand-reviewable; every behavioral rule is CI-tested on Linux. Tile memory per file scales with nBins (a future 8192-FFT pyramid halves slot count — revisit capacity math then). Overlay layering is a one-file swap if profiling demands Metal-drawn overlays. Runtime shader compilation costs a few ms at startup and forgoes offline shader validation — mitigated by keeping the shader tiny and the uniform struct scalar-only.
Alternatives considered: separate IndraKitApple render package (more indirection, same smoke-test surface); 512×256 sub-tiles per §5.3 (unstable keys under frequency navigation); .metal resources via SwiftPM (fragile for executable targets, unverifiable here); overlays in the Metal pass (higher iteration cost now, deferred not rejected); CAMetalDisplayLink pacing (deferred with a named trigger).
